# AIエージェント向け汎用資産の品質チェックリスト

AIエージェント向けに参照させるマークダウンテンプレートやプロンプト全般に流用できる観点を抜き出してチェックリスト化したもの。

## 判定記入項目

各チェックリストに加え、チェックリストの観点で修正が必要なものに関しては下記を追加で記入する。

| 項目 | 内容 |
|---|---|
| 判定 | `△`、`✕`、`N/A` |
| 問題箇所 | 問題のあったファイルなど  |
| 根拠 | 対象箇所、テスト結果、ログ |
| 改善内容 | `✕`時に必要な修正 |
| 適用外理由 | `N/A`とした理由 |

### 判定の定義 

| 判定 | 定義 |
|---|---|
| `△` | 判定基準を満たしているが、修正が推奨されるもの |
| `✕` | 判定基準を満たしておらず、修正が必要 |
| `N/A` | 対象資産の種類、目的、利用環境などから適用対象外 |

## 1. 記述量・情報密度

- [ ] **【重要】記述量が適切である**：主要指示は短く保ち、長くなったら分割する（後述）
  - 良い例：本文は要点だけに絞り、200 行を超えるデプロイ手順の詳細は `workflows/deploy_steps.md` に切り出して本文からリンクする
- [ ] **【重要】AI が持つ前提知識**：一般知識は無条件に説明しない。ただし、省略可否は対象モデル・対象タスクの評価結果で判断し、固有ルール、非自明な制約、安全上の前提は明示する。
  - 良い例：「Git とは分散型バージョン管理…」を省略し、「コミットメッセージは `[種別] 概要` 形式にする」という独自ルールだけ書く

## 2. 指示の厳密さ（自由度の設定）

- [ ] **【重要】タスクの壊れやすさ・変動性に合わせて具体度を調整する**
  - 高自由度：複数の正解がある／文脈依存の判断 → 方向性だけ示す
    - 良い例：「ユーザー向けの説明文は、親しみやすく簡潔なトーンで書く」（文面はモデルに委ねる）
  - 中自由度：推奨パターンがある → テンプレート＋調整余地
    - 良い例：「PR 説明は下記テンプレを埋める。必要に応じて項目を追加してよい」
  - 低自由度：順序・一貫性が重要で壊れやすい → 正確な手順を固定し「変更するな」と明示
    - 良い例：「DB マイグレーションは ①バックアップ → ②適用 → ③検証 の順で実行する。**順序を変更するな**」

## 3. 構造・ナビゲーション

- [ ] **【重要】100行を超えるファイルは目次で構造化する**（先頭に目次 → 部分読みでも全体像が伝わる）
  - 良い例：先頭にセクションへのリンク一覧を置く（本ファイル冒頭の「## 目次」がこれにあたる）

    ```
    ## 目次

    - [1. 記述量・情報密度](#1-記述量情報密度)
    - [2. 指示の厳密さ（自由度の設定）](#2-指示の厳密さ自由度の設定)
    - [3. 構造・ナビゲーション](#3-構造ナビゲーション)
    ```

- [ ] **【重要】参照は浅く**：重要な参照先は入口から直接到達可能にする。深い参照連鎖を使う場合は、参照漏れが起きないナビゲーション、索引、検索手段、読み込み指示を用意する。
  - 良い例：入口の README から `docs/api.md` へ直接リンクする（README → `overview.md` → `api.md` と孫参照させない）・参照の階層が1~2階層以内に収まっている
- [ ] **【重要】ファイル名・見出しは内容が分かる具体名に**（`doc2.md` ではなく `form_validation_rules.md`）
  - 良い例：入力フォームの検証仕様は `form_validation_rules.md`、見出しは「## 必須項目のバリデーション」のように内容が分かる名前にする
- [ ] **【重要】段階的開示と到達性**：概要（入口）→ 詳細は別ファイルに分割。一枚に詰め込まない
  - 良い例：README には概要と使い方の要点だけを書き、詳細な環境構築手順は `docs/setup.md` に分離する
  - 良い例：認証関連は `auth/`、決済関連は `payment/` に分け、認証タスク時に決済の文脈を読ませない
- [ ] **【重要】適用条件を明示する**：「何をする資産か」だけでなく、「いつ使うか」「必要に応じて、いつ使わないか」も記載し、AI が参照・適用の要否を判断できるようにする
  - 良い例：「PDF を生成するときに使う。CSV や Excel を出力するときは使わない」と冒頭に明記する
- [ ] **【重要】重要な情報への到達経路を短くする**：重要度の高いルールや参照先ほど、入口となるファイルや上位セクションから直接たどれるようにする
  - 良い例：「秘密情報をコミットしない」という重大ルールを、深い階層ではなく入口 README の先頭付近に置く


## 4. ワークフロー・検証

- [ ] **【重要】複雑なタスクにはチェックリストを用意する**（AI が応答にコピーして進捗管理できる形）
  - 良い例：次のようなチェックリストを提示し、AI が応答にコピーして状態を更新する

    ```
    - [ ] `./docs/仕様書.md`を確認する
    - [ ] 仕様書に基づいて実装を行った
    - [ ] `./docs/実装報告書.md`を更新した
    ```

- [ ] **【重要】完了条件を明示する**：「どう進めるか」だけでなく、「どの状態になれば完了としてよいか」を定義する。必須項目、検証結果、出力形式などを終了判定に使う
  - 良い例：「全テストが green かつ `npm run build` が成功したら完了とする」
- [ ] **【重要】フィードバックループを組み込む**：「検証 → エラー修正 → 繰り返す」。検証役はスクリプトでも参照ドキュメント（スタイルガイド等）でもよい
  - 良い例：「最大試行回数を定義＋同一エラーが続いた時の停止条件を定義 → `npm run lint` を実行 → 指摘を修正 → 再実行、をエラー 0 件になるまで繰り返す」
- [ ] **【重要】リソースに対する操作意図を明示する**：ファイルやスクリプトについて「読む」「検索する」「実行する」「編集する」のどの操作を行うべきかを曖昧にしない
  - 良い例：「`config.yaml` は**読み取り専用**。設定を変更する場合は `config.local.yaml` を**編集する**」
- [ ] **【重要】条件付き分岐を明示**：判断ポイント（「新規作成なら → A／既存編集なら → B」）で導く
  - 良い例：

    ```
    テーブル追加の場合：create_migration を作成
    テーブル更新の場合：alter_migration を作成
    ```

- [ ] **検証可能な中間成果物を作る**：「計画 → 検証 → 実行」で、実行前に機械的・客観的にチェックしミスを早期発見
  - 良い例：実装前に「変更対象ファイル一覧」を Markdown で出力し、人またはスクリプトが対象範囲を確認してから実装に入る
- [ ] **正常系だけでなく例外時の行動も定義する**：入力不足、参照先の欠落、検証失敗など、予測可能な異常系について「推測する／停止する／代替手段を使う／報告する」などの方針をあらかじめ決める
  - 良い例：「参照先ファイルが存在しない場合は、内容を推測せず処理を停止し、ユーザーに不足を報告する」

## 5. 表現・コンテンツ品質

- [ ] **【重要】用語を統一する**（例：「抽出／取得／取り出す」を混在させない）。一貫性が AI の解析を助ける
  - 良い例：ドキュメント全体でデータ取得の操作を「取得」に統一し、「抽出」「取り出す」を混在させない
- [ ] **【重要】具体例（入出力ペア）を示す**：説明だけより、望ましいスタイル・詳細レベルが正確に伝わる
  - 良い例：入出力ペアで期待結果を示す

    ```
    入力ファイルパス：./docs/input/input-file.md
    出力ファイルパス：./docs/output/output-file.md
     
    入力:
    ユーザー名が未入力の場合、エラーにしてください。

    期待出力:
    {
      "field": "username",
      "code": "required",
      "message": "ユーザー名は必須です"
    }
    ```

- [ ] **【重要】出力テンプレートを提供**：厳密さはニーズに合わせる（固定テンプレ or「基本形＋文脈で調整可」）
  - 良い例：PR 説明のテンプレとして次を提示する

    ```
    ## 概要

    ## 変更点

    ## 確認方法
    ```

- [ ] **【重要】重要なルールは目立たせる**：重大な制約を長文の途中に埋めず、独立した見出し、強い表現（`MUST`／`MUST NOT` など）、配置によって重要度が伝わるようにする
  - 良い例：独立した見出し・強調付きで配置する

    ```
    ## セキュリティ制約

    **MUST NOT**: 認証情報をログに出力しない
    ```

- [ ] **【重要】数値・閾値・回数には根拠を持たせる**：リトライ回数、件数、文字数などの制約はマジックナンバーにせず、目的や終了条件と結び付けて記述する
  - 良い例：「外部 API のリトライは 3 回まで（レート制限が復帰する目安のため）」と根拠を添える
- [ ] **時間依存情報を避ける**：「◯月以降は～」ではなく、現行を本文に・旧情報は「古いパターン」セクションへ隔離
  - 良い例：本文には「現行は v2 API を使う」とだけ書き、v1 の記述は末尾の「## 古いパターン」に隔離する
- [ ] **例は通常ケースだけでなく境界・例外ケースも含める**：具体例を単なる見本ではなく、判断境界や例外時の振る舞いを伝える仕様として使う
  - 良い例：通常入力だけでなく、空文字・最大長超過・`null` に対する期待出力も併記する
- [ ] **選択肢を出しすぎない**：デフォルトを 1 つ提示し、必要な場合の逃げ道（例外条件）だけ添える
  - 良い例：「日付は `YYYY-MM-DD` で出力する。ロケール指定が必要な場合のみ `Intl` を使う」
- [ ] **視点を統一する**（三人称など）：指示文がそのまま別文脈に挿入されても崩れないように
  - 良い例：「対象ファイルを読み込む」のように命令形・三人称で統一し、「私はまず…」のような一人称視点を混ぜない

## 6. 移植性・技術面

- [ ] **【重要】パスは常にスラッシュ(/)**（Windows でもバックスラッシュ(\)を使わない）→ 環境非依存の記述にする、という一般則として流用可
  - 良い例：

    ```
    出力先パス: docs/setup.md
    ```

- [ ] **【重要】実行環境・利用可能な能力を暗黙に仮定しない**：利用可能なツール、ライブラリ、ネットワークアクセス、ファイル操作権限、入力・出力先など、タスク成立に必要な前提条件を明示する
  - 良い例：「本手順はネットワーク接続を前提とする。オフライン時は `./cache` のキャッシュを使う」と前提を明記する
  - 良い例：必要な依存を先頭に列挙する

    ```
    依存:
    - pandas >= 2.0
    - ffmpeg（PATH 上で利用可能なこと）
    ```
- [ ] **決定論的な処理はツールやスクリプトに寄せる**：毎回同じ結果になるべき検証、変換、計算、形式チェックなどは AI に再生成・推論させず、再利用可能な処理として固定する
  - 良い例：合計金額は AI に暗算させず、スクリプトを使って算出する
- [ ] **複数のLLMモデルに対応しているか**：高性能モデルでは過剰な説明になっていないか、小型・高速モデルではガイダンス不足になっていないかを確認する
  - 良い例：手順の要点は箇条書きで明示し（小型モデル向け）、背景の詳しい解説は折りたたみや別セクションに隔離する（高性能モデル向けの冗長化を避ける）
- [ ] **AI の判断と機械的処理を分離する**：AI は解釈・選択・判断に集中させ、客観的に判定できる処理はバリデーターやコードに任せる
  - 良い例：文章のトーンの良し悪しは AI が判断し、文字数上限の超過チェックは linter に任せる
- [ ] **タスクに適した表現形式・モダリティを使う**：レイアウトは画像、数値処理はコード、表は構造化データなど、すべてを自然言語に変換せず AI が扱いやすい形式を選ぶ
  - 良い例：UI レイアウトはスクリーンショット画像、集計処理はコード、一覧データは CSV／表形式で渡す
