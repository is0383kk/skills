# １． FEATURE.md 作成ガイド

このドキュメントは「プロトタイプから少しずつ機能を追加する」ための仕様書を作るためのガイド。

**重要:** 機能追加の段階でも、一度に詰め込むのは1機能（最大でも密接に関連する数機能）まで。
本仕様書に書かれていない機能は、原則として実装しない。

## ■ FEATURE.md の役割

FEATURE.md は Plan モードで機能追加の実装計画を作成するための仕様書としての役割を担う。
PROTOTYPE.md と異なり、「既存仕様への差分」を明確化することが主な責務である。

ユーザーは次の3ステップで機能追加を実装する。
本スキルは **1 のみ** を担当する。Plan モードへの引き渡しを意識して、実装計画の入力として使える粒度に整える。

1. **【本スキル】機能追加のための仕様書を作成し、Plan モードへの移行を促す**
2. Plan モードに移行し、実装計画を立てる
3. 実装計画に沿って機能追加を実装する

## ■ PROTOTYPE.md との違い

| 観点               | PROTOTYPE.md                       | FEATURE.md                                       |
| ------------------ | ---------------------------------- | ------------------------------------------------ |
| 対象               | 最初の動くものを作る               | 既存に対して機能を1つ追加する                    |
| 主な関心事         | 検証したい仮説の最小実装           | 既存仕様との差分・影響範囲                       |
| データモデル       | 主要エンティティ全体を書く         | 差分のみ書く（追加・変更フィールド）             |
| API                | 最小エンドポイント一覧             | 差分のみ書く（追加・変更エンドポイント）         |
| 画面               | 主要画面3枚以内                    | 追加・変更画面のみ                               |
| 既存への影響       | 考慮不要                           | **必ず明記する**（破壊的変更・移行方針）         |

# ２．作成手順

```
作成進捗:
- [ ] Step 1: 既存仕様書の把握とテンプレート読み込み
- [ ] Step 2: ヒアリング（セクション逆引き方式）
- [ ] Step 3: FEATURE.md の作成
- [ ] Step 4: 自己レビュー
- [ ] Step 5: ユーザーへの共有とフィードバック反映
- [ ] Step 6: Plan モードへの引き渡し提案
```

## ■ Step 1: 既存仕様書の把握とテンプレート読み込み

1. 既存の仕様書（`docs/PROTOTYPE.md` および過去の `docs/FEATURE-*.md`）を読み込み、現在の状態を把握する
   - とくに「やらないこと」「コア機能」「データモデル」「API」「画面」を把握しておく
   - 「やらないこと」に挙げていた項目を今回追加する場合、その意思決定が変わったことをユーザーに明示確認する
2. テンプレート（`assets/FEATURE.md`）の構造を把握する
3. テンプレートの構造からヒアリング項目を検討する
4. 出力ファイル名に使う「機能名（日本語）」を確定する
   - 出力パスは `docs/FEATURE-{機能名（日本語）}.md`（例: `docs/FEATURE-お気に入り登録.md`）
   - 既存の `docs/FEATURE-*.md` と重複しないこと
   - ファイル名にOSで使えない文字（`/ \ : * ? " < > |`）や空白は使わない。スペースは使わず、必要なら中黒（`・`）で区切る
   - 機能ID（F-XXX）・画面ID（S-XXX）の連番は、ファイル名とは独立に既存の最大値の次を割り当てる

### ＜テンプレート構造＞

| セクション             | 内容                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| 1. 追加機能の概要      | 機能名 / 一言説明 / 追加する背景 / 対象ユーザー / 達成したいこと / 既存仕様書との関係 / やらないこと        |
| 2. 機能仕様            | 入力・出力・主要ロジック・主要なエラーケース・受け入れ条件・操作の流れ・最小の異常系・既存機能との関係     |
| 3. 既存への影響範囲    | 影響を受ける既存機能 / 既存仕様書の更新箇所 / 移行・後方互換                                                |
| 4. データモデルの差分  | 追加・変更エンティティのER図とフィールド / マイグレーション方針                                             |
| 5. API の差分          | 追加・変更エンドポイント                                                                                    |
| 6. 画面の差分          | 追加・変更画面 + 差分の遷移図                                                                               |
| 7. 次のアクション      | Plan モードへの引き渡し以降のチェックリスト                                                                 |

## ■ Step 2: ヒアリング（セクション逆引き方式）

固定の質問シートは持たない。
入力情報や参照ファイルがないか確認する。
テンプレートの各セクションを順に開き、**そのセクションを埋めるために必要な情報** をユーザーから引き出す質問を、その場で生成する。

進め方の原則:

- **既存仕様書を先に読む**: ヒアリング前に PROTOTYPE.md と過去の FEATURE-*.md を読み、ユーザーに質問する前に「既存仕様から読み取れること」と「読み取れないこと」を分けておく。読み取れることはユーザーには確認だけ求める
- **7セクションを順番にカバーする**: 1.概要 → 2.機能仕様 → 3.既存への影響 → 4.データモデルの差分 → 5.APIの差分 → 6.画面の差分 → 7.次のアクション の順
- **1セクションずつ確定させる**: 全質問を一気に投げない
- **質問は3〜5個に絞る**: 個人開発者が一度に答えられる量に
- **追加の動機を最初に確認する**: なぜ今この機能を追加したいのかを最初に明確にする。動機が曖昧な場合、後続のセクションで判断軸がぶれる
- **影響範囲は推測しない**: 既存機能への影響は、コードや既存仕様を確認した上で記載する。確認が取れない箇所は `（要確認: 理由）` で明記する

セクションごとの質問の方向（実際の質問はその場で文脈に合わせて生成すること）:

- **1. 追加機能の概要**: 追加する背景・動機（プロトを動かしてみて見えた具体的な不便） / この機能で達成したいこと / 既存のターゲットユーザーと同じか / やらないこと（この機能の範囲外）
- **2. 機能仕様**: 入力・出力・主要ロジック / 主要なエラーケース / ハッピーパスの操作の流れ / 既存機能との関係（連携 / 置き換え / 独立）
- **3. 既存への影響範囲**: 影響を受ける既存機能の特定 / 破壊的変更の有無 / 既存データの移行方針 / フィーチャーフラグの要否
- **4. データモデルの差分**: 追加エンティティ・追加フィールド / 既存フィールドの変更（型変更・必須化など）/ マイグレーション方針
- **5. API の差分**: 追加・変更エンドポイント / 既存エンドポイントの破壊的変更の有無
- **6. 画面の差分**: 追加画面 / 既存画面への変更 / 主な遷移先の追加・変更
- **7. 次のアクション**: 通常はテンプレートの定型でOK

## ■ Step 3: FEATURE.md の作成

次の「作成時の注意」と「各セクションの記入例」に従い FEATURE.md を作成してください。

### ＜作成時の注意＞

**前提**: SKILL.md の「■ 共通の原則」（テンプレート構造の不改変／プレースホルダ記法／要確認の表記／空欄の扱い／Mermaid 記法／過剰な記述の回避／「やらないこと」の必須化）はすべて本ガイドにも適用される。本セクションでは、それに加えて機能追加仕様書に固有の注意のみを記載する。

- **差分のみを書く**: 既存仕様書に書かれていることを再掲しない。変更がない場合は「変更なし」と明記する
- **影響範囲は控えめに見積もらない**: 「念のため」で影響範囲に挙げてもよい。後で「影響なし」と確定する分には問題ないが、見落としは大きな手戻りになる
- **破壊的変更は隠さない**: 既存挙動が変わる箇所は「破壊的変更: あり」と明記する。「ほぼ互換」のような曖昧な表現を避ける
- **「やらないこと」は1項目以上**: 機能追加でもスコープを切ることが完走の要。動機がぶれない範囲で何を範囲外にするかを明示する
- **画面の「状態」は当該画面に存在しないものを省略する**: 純表示画面の「入力中」、モーダルの「読み込み中」など、その画面に存在しない状態行は削除してよい（SKILL.md 共通原則 6 のテンプレート改変例外に該当）
- **連番を守る**: 機能IDは既存の最大値の次（例: 既存が F-001, F-002 なら F-003）。画面IDも同様

### ＜各セクションの記入例＞

ユーザーが具体的なイメージを掴めない場合、次の例を提示して引き出すとよい。

**「やらないこと」の例（この機能の範囲外を明確化）**

機能追加では、機能のスコープを限定するために「やらないこと」を必ず書く。

- 〇〇機能との連携
- 通知機能との連動
- 一括処理（今回は単件のみ）
- 検索・フィルタの追加
- 編集履歴の保存

**「既存機能との関係」の例**

追加する機能が既存のどこに位置づくかを明確化する。

- F-001 と独立。共通のデータストアを参照するのみ
- F-002 の出力を入力として受け取る（F-002 → F-XXX の連携）
- F-003 を置き換える（F-003 は廃止）

**「破壊的変更」の判定例**

| 変更内容                                       | 破壊的変更 |
| ---------------------------------------------- | ---------- |
| 新しいAPIエンドポイントを追加                  | なし       |
| 既存APIのレスポンスにフィールドを追加（任意）  | なし       |
| 既存APIのレスポンスからフィールドを削除        | あり       |
| 既存テーブルにNULL不可カラムを追加             | あり       |
| 既存テーブルにNULL許容カラムを追加             | なし       |
| 既存画面の挙動が変わる（クリックで別画面に遷移）| あり       |

## ■ Step 4: 自己レビュー

ユーザーへ提示する前に、次の観点で確認する。

1. **セクションの充足**: 7セクションすべてに記述があるか（空欄＋`（要確認）`は可、無記載はNG。差分がない場合は「変更なし」と明記）
2. **追加の動機が具体的か**: 「使いやすくしたい」のような抽象表現になっていないか。プロトタイプ運用や実体験に紐づいているか
3. **「やらないこと」が1項目以上記載されているか**: 機能追加でもスコープを切ることが重要。0項目はNG
4. **影響範囲の網羅性**: 既存機能の一覧と照合し、影響を受ける可能性のあるものをすべて挙げているか
5. **破壊的変更の明示**: 破壊的変更がある場合、「3. 既存への影響範囲」と「5. APIの差分」の両方で一貫して明記されているか
6. **差分のみを書いているか**: 既存仕様書のコピーになっていないか
7. **ID・ファイル名の整合性**: 機能ID（F-XXX）・画面ID（S-XXX）の連番が既存と矛盾していないか / 出力ファイル名 `docs/FEATURE-{機能名（日本語）}.md` が既存と重複せず、使用不可文字を含んでいないか
8. **要確認の妥当性**: 推測で書いた箇所にだけ `（要確認: 理由）` が付いているか
9. **プレースホルダ残存チェック**: テンプレートの `{…}` ガイド文がそのまま残っていないか（実値で置換、もしくは `（要確認: 未決定）` に置き換わっているか）
10. **Mermaid構文**: ノードラベルにカッコ等を含む場合のダブルクォート囲みが守られているか
11. **既存仕様書の更新箇所が明示されているか**: 更新が必要な場合、どのファイルのどこを更新するかが書かれているか

問題があれば修正してからユーザーに提示する。

## ■ Step 5: ユーザーへの共有とフィードバック反映

- 生成完了後、出力先パス（`docs/FEATURE-{機能名（日本語）}.md`）を共有する
- とくに「追加の動機が腹落ちするか」「やらないことに納得感があるか」「影響範囲・破壊的変更の認識が合っているか」を重点的に確認してもらう
- フィードバックを受けて修正する場合も、Step 3 の作成方針と Step 4 のレビュー観点を守る

## ■ Step 6: Plan モードへの引き渡し提案

仕様書が確定したら、ユーザに Plan モードに移行できる旨を伝える。
ステップはここで終了。実装計画とコード生成は Plan モード以降の責務。

なお、本仕様書の確定により既存仕様書（PROTOTYPE.md / 過去のFEATURE.md）の更新が必要な場合は、Plan モード移行時にその旨も併せて伝える。
