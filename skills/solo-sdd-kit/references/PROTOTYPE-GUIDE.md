# １． PROTOTYPE.md 作成ガイド

このドキュメントは「最初のプロトタイプを動かしてみる」ための最小仕様書を作るためのガイド。

**重要:** プロトタイプ段階では「検証に必要な最小範囲」だけを実装する。
この仕様書に書かれていない機能は、原則として実装しない。

## ■ PROTOTYPE.md の役割

PROTOTYPE.md は Plan モードでプロトタイプの実装計画を作成するための仕様書としての役割を担う。

ユーザーは次の3ステップでプロトタイプを実装する。
本スキルは **1 のみ** を担当する。Plan モードへの引き渡しを意識して、実装計画の入力として使える粒度に整える。

1. **【本スキル】プロトタイプのための仕様書を作成し、Plan モードへの移行を促す**
2. Plan モードに移行し、実装計画を立てる
3. 実装計画に沿ってプロトタイプを実装する

# ２．作成手順

```
作成進捗:
- [ ] Step 1: テンプレート読み込みとヒアリング項目の検討
- [ ] Step 2: ヒアリング（セクション逆引き方式）
- [ ] Step 3: PROTOTYPE.md の作成
- [ ] Step 4: 自己レビュー
- [ ] Step 5: ユーザーへの共有とフィードバック反映
- [ ] Step 6: Plan モードへの引き渡し提案
```

## ■ Step 1: テンプレート読み込みとヒアリング項目の検討

1. テンプレート（`assets/PROTOTYPE.md`） の構造を把握する
2. テンプレートの構造からヒアリング項目を検討する

### ＜テンプレート構造＞

| セクション              | 内容                                                                                                     |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| 1. 概要                 | プロダクト名 / 一言説明 / 解決したい課題 / ターゲット / 検証したいこと / やらないこと                    |
| 2. コア機能             | 機能を1〜3個に絞り、入力・出力・主要ロジック・主要なエラーケース・受け入れ条件・操作の流れ・最小の異常系 |
| 3. 技術スタック・構成   | 言語/FW/DB/ホスティング/認証 + 制約（コスト上限など） + Mermaid構成図                                    |
| 4. データモデル（最小） | 主要エンティティ3〜5個のER図とフィールド一覧                                                             |
| 5. API スケッチ         | コア機能を満たす最小エンドポイント一覧                                                                   |
| 6. 画面スケッチ         | 主要画面3枚以内 + 画面遷移図                                                                             |
| 7. 次のアクション       | Plan モードへの引き渡し以降のチェックリスト                                                              |

## ■ Step 2: ヒアリング（セクション逆引き方式）

固定の質問シートは持たない。
入力情報や参照ファイルがないか確認する。
テンプレートの各セクションを順に開き、**そのセクションを埋めるために必要な情報** をユーザーから引き出す質問を、その場で生成する。

進め方の原則:

- **7セクションを順番にカバーする**: 1.概要 → 2.コア機能 → 3.技術スタック・構成 → 4.データモデル → 5.API スケッチ → 6.画面スケッチ → 7.次のアクション の順で進めると、上流の決定が下流の質問を絞り込んでくれる
- **1セクションずつ確定させる**: 全質問を一気に投げない。1セクション分の質問 → ユーザー回答 → そのセクションを仮埋め → 次セクション、のリズム
- **質問は3〜5個に絞る**: 個人開発者が一度に答えられる量に。
- **既知の情報は質問しない**: ユーザーが先に提示したメモ・チャット履歴・ファイルに答えがある項目は読み取って埋め、ユーザーには確認だけ求める
- **「今わかる範囲で」の前提**: 答えにくい項目は「現時点では未定」「後で決める」も有効な選択肢として提示する

セクションごとの質問の方向（実際の質問はその場で文脈に合わせて生成すること）:

- **1. 概要**: プロダクトの一言説明 / 解決したい課題（具体的な不便、抽象論ではなく実体験ベース）/ 想定ユーザー（ペルソナ1人または1セグメント）/ プロトで何を確かめたいか（動かして「何が分かれば成功か」）/ やらないこと
- **2. コア機能**: コア機能を1〜3個に絞る / 機能ごとの入力・出力・主要ロジック / 主要なエラーケースと最低限の挙動（「何もしない / リトライ / 画面表示」のどれか）/ ハッピーパスの操作の流れ / 最低限扱う異常系
- **3. 技術スタック・構成**: 既に得意な言語・FW / コスト上限 / デプロイ先（無料枠 / 既契約 / 新規契約）/ 認証の要否 / 既に手元にあるアカウント・APIキー / 対象ブラウザ・実行環境 / 開発に使える時間
- **4. データモデル**: 主要エンティティ（3〜5個）と主なフィールド
- **5. API スケッチ**: コア機能を満たす最小エンドポイントのみ。認証・バリデーション・エラーフォーマットの詳細はプロトタイプ段階では掘らない
- **6. 画面スケッチ**: 主要画面（3枚以内）/ 画面ごとの役割・主な要素・状態（初期/読み込み/成功/エラー）/ 主な遷移先
- **7. 次のアクション**: 通常はテンプレートの定型でOK。プロジェクト固有の前後工程があれば確認

## ■ Step 3: PROTOTYPE.md の作成

次の「作成時の注意」と「各セクションの記入例」に従い PROTOTYPE.md を作成してください。

### ＜作成時の注意＞

**前提**: SKILL.md の「■ 共通の原則」（テンプレート構造の不改変／プレースホルダ記法／要確認の表記／空欄の扱い／Mermaid 記法／過剰な記述の回避／「やらないこと」の必須化）はすべて本ガイドにも適用される。本セクションでは、それに加えてプロトタイプ仕様書に固有の注意のみを記載する。

- **コア機能は1〜3個に絞る**: ヒアリングで4個以上挙がったら、「プロトで真っ先に動かすのはどれ？」を確認して3個以内に収束させる。残りは「やらないこと」に追いやる。「あったら便利」は全部やらないことリストへ
- **「やらないこと」は3〜5項目**: プロトタイプ段階では検証範囲を明確にするためにこの粒度を守る
- **画面の「状態」は当該画面に存在しないものを省略する**: 純表示画面の「入力中」、モーダルの「読み込み中」など、その画面に存在しない状態行は削除してよい（SKILL.md 共通原則 6 のテンプレート改変例外に該当）
- **構成図はプロトタイプ用途に絞る**: 「動けばOK」の粒度を超える本番運用議論は持ち込まない

### ＜各セクションの記入例＞

ユーザーが具体的なイメージを掴めない場合、次の例を提示して引き出すとよい。

**「やらないこと」の例（3〜5項目を目安）**

プロトタイプでは実装しない項目。  
Plan 作成時・実装時にもタスク化しない。3〜5項目を目安に書き出す。

- ユーザー認証
- 課金
- 管理画面
- 高度な権限管理
- 本番運用を前提とした監視・冗長化
- 複雑な設定画面
- 多言語対応

**コア機能の「受け入れ条件」の例**

この機能が完成したと言える条件。

- [ ] 入力フォームに値を入れて送信できる
- [ ] 正常時は結果画面に期待結果が表示される
- [ ] 入力が空の場合はエラーメッセージを表示する
- [ ] ローディング中は処理中であることが分かる
- [ ] 主要なエラーケースで画面がクラッシュしない

**最小の異常系の方針**

プロトタイプで最低限扱う異常系のみを書く。

| ケース       | 最低限の挙動                             |
| ------------ | ---------------------------------------- |
| 入力不足     | 画面にエラーメッセージを表示する         |
| 外部API失敗  | リトライせず、失敗したことを表示する     |
| 想定外エラー | 画面全体を落とさず、汎用エラーを表示する |

## ■ Step 4: 自己レビュー

ユーザーへ提示する前に、次の観点で確認する。

1. **セクションの充足**: 7セクションすべてに記述があるか（空欄＋`（要確認）`は可、無記載はNG）
2. **コア機能が1〜3個に絞られているか**: 4個以上書かれていたら絞り込む。使わない F-XXX ブロックは削除されているか
3. **「やらないこと」が3〜5項目書かれているか**: 0〜2項目しかない場合、ヒアリングで深掘りが足りていない可能性が高い
4. **検証したいことが具体的か**: 「使ってもらえるか試したい」のような抽象表現になっていないか
5. **要確認の妥当性**: 推測で書いた箇所にだけ `（要確認: 理由）` が付いているか
6. **プレースホルダ残存チェック**: テンプレートの `{…}` ガイド文がそのまま残っていないか（実値で置換、もしくは `（要確認: 未決定）` に置き換わっているか）
7. **個人開発適性**: SLA目標・冗長構成・厳密なテストカバレッジ目標など、プロトタイプには過剰な記述が紛れ込んでいないか
8. **Mermaid構文**: ノードラベルにカッコ等を含む場合のダブルクォート囲みが守られているか
9. **画面数**: 主要画面が3枚以内に収まっているか（超えている場合は重要度の低いものを削るか「やらないこと」に移す）
10. **APIの最小性**: 認証・バリデーション・エラーフォーマットの詳細など、プロトタイプには不要な記述が紛れ込んでいないか

問題があれば修正してからユーザーに提示する。

## ■ Step 5: ユーザーへの共有とフィードバック反映

- 生成完了後、出力先パス（`docs/PROTOTYPE.md`）を共有する
- とくに「コア機能が1〜3個に絞れているか」「やらないことに納得感があるか」を重点的に確認してもらう
- フィードバックを受けて修正する場合も、Step 3 の作成方針と Step 4 のレビュー観点を守る

## ■ Step 6: Plan モードへの引き渡し提案

仕様書が確定したら、ユーザに Plan モードに移行できる旨を伝える。
ステップはここで終了。実装計画とコード生成は Plan モード以降の責務。
