# converter-docx

Wordファイル（`.docx` / `.doc`）と Markdown の双方向変換を担う。

- 既存の Word 文書を AI 駆動開発で扱いやすい Markdown に変換する（**正方向**）
- 編集済み Markdown を Word 文書に戻す（**逆方向**）

組み込みの `docx` スキル（`Skill(docx)`）を土台に使い、対象ファイルや指示の文脈から方向を判断して動く。

## 想定する利用シーン

このスキルは特定のプロセス標準に縛られない**汎用ドキュメント変換スキル**として使える。具体的には次のような場面を想定する。

- 業務資料・配布資料・参考資料を Markdown で整理し、AI に読み解かせる
- 顧客や他部署から受領した Word 資料を取り込み、編集後にもとの形式に戻す
- 議事録・仕様書・社内手順書など、プロセス標準の成果物を雛形と Markdown の間で往復させる
- 過去の電子資料を、検索・差分管理しやすい Markdown 資産へ転換する

## 起動条件と方向の判定

呼び出された文脈から、まず「どちらの方向か」を決める。判定は次の優先順で行う。

1. ユーザーが明示している場合はそれに従う（例: 「Markdown を docx に戻して」「Word を md 化して」）
2. 入力ファイルが `.docx` / `.doc` のみなら **Markdown化（正方向）**
3. 入力ファイルが `.md` のみなら **Word化（逆方向）**
4. 両方含まれている場合は、ユーザーへ意図を確認する

判別が付かないときは推測で進めず、対象ファイル・出力先・方向をユーザーに確認する。

## 共通方針

- 出力先は原則として変換元と同じディレクトリ。ファイル名は拡張子だけを差し替える（`XXXX.docx` ⇔ `XXXX.md`）
- 出力先がすでに存在する場合は、上書きしてよいかをユーザーに確認する
- Word の見た目（レイアウト・装飾）の再現を目的にしない。情報の構造と内容を双方向で保つことを優先する
- 「以下は変換結果です」のような前置きや、変換ルールそのものの説明、変換処理の言い訳は本文に書かない
- 不要なコードブロックで全体を囲わない

## Step 1: 方向に応じて参照ドキュメントを読む

- **Markdown化（docx → md）** の場合は `references/docx_to_markdown.md` を読む
- **Word化（md → docx）** の場合は `references/markdown_to_docx.md` を読む

各リファレンスには、変換ルール・整形方針・禁止事項・推奨フローがまとまっている。SKILL.md 本体には共通事項のみを置き、形式特有の細部はリファレンス側に寄せている。

## Step 2: 入出力の確認

- 変換対象（ファイルパス／フォルダパス）が指定されていることを確認する
- フォルダ指定の場合は、配下の対象拡張子をすべて変換する
- **逆方向**でフォーマット（雛形 `.docx`）が指定されている場合は、その見出しスタイル・段落スタイルを尊重する。指定がなければ、Markdown の構造に素直に従って生成する

## Step 3: 変換の実行

- 変換中は、対象ファイル名と方向を1行で報告する程度にとどめる
- 文字コードは UTF-8、改行コードは LF を基本としつつ、既存ファイルがある場合はそれを尊重する
- 図・作業フローなど Mermaid で表現できるものは、正方向では Mermaid 化、逆方向では `mermaid-js/mermaid-cli` で画像化して埋め込む

## Step 4: 結果報告

- 入力 → 出力のパスを列挙する
- 推測で補った箇所がある場合は本文中に `（要確認: 理由）` をインラインで残し、報告でも触れる
- 変換できなかった要素（読み取れない図、判読不能な箇所、画像化に失敗した Mermaid など）があれば、その旨を簡潔に伝える

## 禁止事項

- Word の見た目やレイアウト再現を目的とした記述
- 変換ルールそのものや、Word/Markdown の操作説明の出力
- 校閲コメント・変更履歴の本文への混入
- 推測による無理な補完（特に逆方向で雛形のスタイルを勝手に変える）
- 「以下は変換結果です」などの前置き
